# 长时间监控场景的适配分析

> 这份文档回答一个问题：**如果把现在的系统从"分析一段短视频"改成"持续看监控"，
> 会在哪里崩掉，需要换什么。**
>
> 课程要求只到"支持短视频、结合多个时间点信息"，本文属于超出要求的技术延伸，
> 目的是答辩时能回答"这套东西能不能真上生产"。所有结论都基于本仓库代码实测，
> 不是文献转述。

---

## 一、先看现状：我们的实测边界

### 1.1 现有抽帧策略

`src/tools.py` 的 `VideoFrameExtractor` 做的是**固定数量、时间轴均匀采样**：

```python
positions = [frame_count * (i + 0.5) / max_frames for i in range(max_frames)]
```

默认 `max_video_frames = 4`（`src/pipeline.py`）。

这个设计在短视频上没问题（12 秒 / 4 帧 = 每 3 秒一帧，够用）。
但它有一个致命性质：**帧间隔随时长线性放大**。

| 视频时长 | 抽 4 帧的间隔 |
| --- | --- |
| 12 秒 | 3 秒 |
| 1 分钟 | 15 秒 |
| 4 分钟 | 60 秒 |
| 1 小时 | 15 分钟 |

也就是说，**视频越长，看得越稀疏**。这是"长时间监控"最根本的矛盾。

### 1.2 实测：4 分钟视频里一个 3 秒的异常，必然漏掉

构造了一段测试视频（`scripts/make_long_video.py`）：

- 总长 240 秒，10 fps，2400 帧
- 前 120 秒与后 117 秒是正常实验室画面
- **第 120~123 秒插入危险画面**（电热板旁堆纸箱）

用默认配置跑（`python src/main.py analyze --input long_240s_event120.mp4`）：

```
系统形态：multi_agent｜模式：api｜策略：v0.4｜帧数：4
风险条目：1（高风险 1）｜Agent 分歧：0 处
成本：模型调用 12 次｜工具调用 5 次｜耗时 48348 ms
```

抽帧位置算出来是 **30 / 90 / 150 / 210 秒**，而异常在 120~123 秒 ——
**四个采样点全部跳过，一次都没落在异常上。**

提高帧数才命中：

| 抽帧数 | 帧间隔 | 抽帧位置示例 | 是否命中 120~123 秒 |
| --- | --- | --- | --- |
| 4（默认） | 60.0s | 30, 90, 150, 210 | ✗ |
| 8 | 30.0s | 15, 45, 75, 105 … | ✗ |
| 16 | 15.0s | 8, 22, 38, 52 … | ✗ |
| 32 | 7.5s | 4, 11, 19, 26 … | ✗ |
| **64** | **3.8s** | … 116, **121.8**, 125 … | **✓ 第 33 帧** |
| 128 | 1.9s | … | ✓ |

**结论：要让 4 分钟视频不漏掉一个 3 秒的事件，至少需要 64 帧。**
（一般规律：帧间隔必须小于事件最短持续时间。）

### 1.3 命中之后：模型是能看出来的

单独分析第 33 帧（121.8 秒那张危险画面）：

| 输入 | 判定 | 等级 | 置信度 | 证据 |
| --- | --- | --- | --- | --- |
| 命中帧（真异常） | `flammable_near_heat` | high | **0.85** | "加热器周围有电线和纸制品，靠近热源可能导致火灾风险" |
| 4 帧长视频（未命中） | `flammable_near_heat` | high | **1.00** | "酒精灯正在燃烧，火焰距离烧杯和试管非常近" |

**识别能力没问题，问题全在采样策略。** 而且注意后一行——那是个误报，
置信度却比真阳性还高。下面说为什么。

## 二、三个必须知道的失效模式

### 2.1 失效一：漏检（采样密度不足）

上面已经量化。这不是模型能力问题，是工程参数问题：
**固定帧数 = 视频越长盲区越大。**

### 2.2 失效二：重复帧被当成"持续证据"（虚假一致性）

这次实验还炸出一个更隐蔽的问题。

那段视频里正常画面每 3 秒轮换一张，而抽帧点在 30/90/150/210 秒 ——
**全是 3 的倍数**，结果抽到的 4 帧是同一张图：

```
帧1 与帧1 平均像素差 = 0.00
帧2 与帧1 平均像素差 = 0.00
帧3 与帧1 平均像素差 = 0.40   ← 只是 JPEG 压缩噪声
帧4 与帧1 平均像素差 = 0.40
```

4 帧几乎完全相同，**12 次模型调用全花在同一个画面上，信息增益为零**。

更糟的是 `_temporal_fuse` 的处理（`src/pipeline.py`）：

```python
item.persistence = frames_seen / total_frames          # 4/4 = 1.0
if item.persistence >= 0.5:
    item.confidence = min(item.confidence + PERSISTENT_BONUS, 1.0)   # 封顶 1.0
```

它把"同一画面重复出现 4 次"当成"这个风险持续了 100% 的帧"，
于是加置信度、保持 `confirmed`，报告里写：

> 第 1~4 帧（持续 4/4 帧，占 100%）

**这是系统自己制造的强证据。** 而那张图的真值是什么？
在 `data/web_labels_dev.csv` 里：`web_38093862`，真值 **normal**，
备注写着"酒精灯加热烧杯但周边无可燃物，属规范操作（**容易被误判为热源旁易燃物**）"。

所以实际发生的是：**一个易混淆样本 → 被判成 high → 因重复帧加成升到置信度 1.0 → confirmed。**

这也解释了为什么出现"假阳性置信度 1.00 > 真阳性 0.85"的倒挂。
**在当前实现里，置信度不能用来排序谁更可能是真的。**

### 2.3 失效三：处理时间超过视频时长

按实测单次调用 4.03 秒推算（4 帧 12 次调用 = 48.3 秒）：

| 抽帧数 | 帧间隔 | 调用次数 | 预估耗时 | 相对视频时长（240s） |
| --- | --- | --- | --- | --- |
| 4（默认） | 60.0s | 12 | 48 秒 | 0.2 倍 |
| 16 | 15.0s | 48 | 193 秒 | 0.8 倍 |
| 32 | 7.5s | 96 | 387 秒 | 1.6 倍 |
| **64**（能覆盖 3 秒事件） | 3.8s | **192** | **774 秒 ≈ 12.9 分钟** | **3.2 倍** |
| 240（1 fps） | 1.0s | 720 | 2901 秒 ≈ 48 分钟 | 12.1 倍 |

**要保证不漏检，就得花 3.2 倍于视频时长的时间来处理。**
这是"准实时"的硬上限：现在的架构**永远追不上**，因为需求是密度 ↑、而密度直接换成本 ↑。

## 三、开源方案怎么选（含两处信息修正）

按"能不能直接补上我们缺的能力"分两类。

### 3.1 路径一：持续观察、实时交互

**京东 JoyAI-VL-Interaction**（2026-06 开源，全栈含部署方案，vLLM-Omni day-0 支持）

它的核心设计不是"更准"，而是**模型自己决定什么时候说话、什么时候沉默**，
并且能在遇到复杂任务时把活儿交给后台 Agent，自己继续盯着画面：

> "前台实时助手 + 后台智能大脑"——前台负责在场，后台负责干重活。

**这条对我们最有价值，因为它的分层和我们现有架构是同构的**：
我们的三 Agent（感知 → 分析 → 复核）天生就是那个"后台"。
换句话说，我们不需要重写系统去追视频基础模型，
而是可以把自己定位成**接在实时层后面的语义推理层**。

它还有一句判断标准值得抄进报告：

> "对实时交互来说，会说话很重要，会沉默也同样重要。"

这正是我们做**弃权（abstain）和复核驳回**的理论依据——
误报抑制不是缺陷修补，而是这类系统的核心能力。

**VideoChat3**（南大 + 上海 AI Lab + 南洋理工 + 北大，4B，2026-07，论文 arXiv:2607.14935）

全栈开源（权重 + 训练代码 + 策略 + 数据集）。关键设计是 `I3D-ViT`
把时序建模前移到视觉编码阶段（约 16 倍时空压缩），以及**三态流式感知**：

| 状态 | 含义 | 对应我们的 |
| --- | --- | --- |
| Silence | 无相关证据，低功耗观察 | `abstain`（弃权） |
| Standby | 出现潜在线索，提高下一窗口分辨率 | `uncertain` |
| Response | 证据充分，输出后回归低功耗 | `confirmed` |

这个对应关系不是牵强——**它说明我们做的"三态决策"在架构上是站得住的**，
只是我们目前是"一次性判完"，而不是"持续降级观察 / 按需提分辨率"。

### 3.2 路径二：长视频回溯、异常检测

**SigMamba-V1**（SigLIP2 + Mamba，弱监督视频异常检测）

**这里有两处必须修正的说法：**

1. **"从根本上避免了 Transformer 的二次方成本"——不准确。**
   官方仓库自己写明：`SigLIP2 is a vision encoder model which is transformers based.
   So it has O(N²) complexity.` Mamba 部分只有约 **32M 参数**，线性复杂度只体现在
   **时序建模**这一段；视觉编码仍是二次方。所以它不是"长视频无成本"，而是
   "把二次方那一段压小了"。

2. **AUC 89.82% 不等于可用。** 同一份 benchmark 里：

   | 指标 | Large | Small |
   | --- | --- | --- |
   | AUC-ROC | 89.82% | 87.57% |
   | **Average Precision** | **41.05%** | 32.04% |
   | **Best F1** | **41.18%** | 41.90% |
   | 推理速度 | 1,022 FPS | 3,242 FPS |
   | 峰值显存 | 5,148 MB | 3,207 MB |

   异常检测是极不平衡问题，AUC 好看是因为它衡量的是排序能力；
   但 AP 和 F1 都在 41% 左右，意味着**真报警里一半以上是误报**。

   这恰好印证了我们实验里的核心结论：**这类系统的主要矛盾是误报，不是漏报。**
   我们多 Agent 组把误报率从 79.1% 压到 14.0%，代价是漏报翻倍——
   换成任何单模型方案，同样要面对这个权衡，不会自动消失。

   另外注意：它推荐 `num_frames=32`，处理的是**固定长度窗口**，不是"小时级连续流"。
   真上小时级仍然要滑窗 + 聚合，聚合怎么做又回到我们踩过的坑（见 2.2）。

**Video-XL / InternVideo2.5**：面向"事后在长录像里定位某事件"，
和我们的场景（实时判断当下是否危险）不同。适合做**复盘检索**，不适合做预警。

### 3.3 边缘侧

| 模型 | 规模 | 定位 |
| --- | --- | --- |
| Memories-S0 | 3B | 安防领域 VideoLLM，token 动态剪枝，Apache 2.0 |
| LFM2.5-VL-450M | 450M | 4 FPS 逐帧理解，可在 CPU/嵌入式运行 |

边缘模型的价值不在精度，在**"能一直开着"**。对我们这个课程项目，
现实意义是：轻量模型做**门控**（先筛有没有变化），重模型只在候选片段上跑。

### 3.4 信息核实状态

| 说法 | 状态 |
| --- | --- |
| JoyAI-VL-Interaction 全栈开源、vLLM-Omni 原生支持、"前台+后台 Agent" | ✅ 已核实（多方报道一致） |
| VideoChat3 4B、南大+上海AI Lab+南洋理工+北大、全栈开源、三态流式 | ✅ 已核实（论文 arXiv:2607.14935 + 项目主页） |

## 四、如果要做，怎么改（不动基础模型）

三步，从便宜到贵。前两步都能在现在的代码上做，不需要 GPU、不需要换模型。

### 第一步：帧去重（修 bug，不是优化）

**问题**：重复帧被当成持续证据，把误报升成置信度 1.0（见 2.2）。

**做法**：抽帧后先算相似度（直方图 / pHash / 帧差），
近似重复的帧只送模型一次，但**记录它代表的时间跨度**。

**关键点：`persistence` 必须按"时间"算，不能按"帧数占比"算。**
现在 `frames_seen / total_frames` 的分母是抽帧数，
一旦抽帧密度变了，同一个场景的 persistence 就跟着变——这是量纲错误。

这一改同时省算力：4 帧重复图从 12 次调用降到 3 次。

### 第二步：门控式两阶段（把成本从"随时长线性"改成"随事件数线性"）

```
连续流 ──[帧差/运动检测]──> 静止 → 丢弃（不调模型）
                    └──> 有变化 → 进候选队列 ──> 多 Agent 分析
```

这就是 VideoChat3 的 Silence/Standby 和 vinfer 的"运动检测门控"在做的事。
对我们这种**长时间静止、偶发危险**的实验室场景，命中率提升会非常直观：
4 分钟视频里真正需要分析的片段可能只有十几秒。

### 第三步：事件级状态机（对应课程"结合多个时间点"的进阶形态）

现在的融合是"看完所有帧再合并"，输出一次性结论。
真正持续监控需要的是**带记忆的状态机**：

```
Silence ──线索──> Standby ──证据累积──> Response ──处置后──> Silence
   ↑                                                          │
   └────────────────── 冷却期，避免反复报警 ──────────────────┘
```

这样才能表达"同一个风险持续了多久""中间消失过没有""是不是第二次出现"，
也是抑制重复报警（告警疲劳）的唯一办法。

## 五、这份分析对课程项目的意义

**必须说清楚：上面的改动我们没有实施，现在的系统仍然是"短视频分析"。**
课程要求到此为止，硬上长时间监控会让实验结论和现有数据集对不上
（84 个样本全是静态图或 12 秒片段）。

但这份分析有三个可以直接用在答辩里的价值：

1. **证明我们知道自己系统的边界。** 被问"能不能上生产"时，
   拿 2.1 的表格和 2.3 的时间倍率回答，比说"可以扩展"扎实。
2. **2.2 是一个真实的架构缺陷，不是能力不足。** 它说明
   "多帧一致"这个看似稳妥的设计，在重复帧面前会反向放大错误。
   已收录进 `docs/失败案例记录.md`。
3. **误报才是主要矛盾。** SigMamba 那组数据（AUC 89.8% 但 F1 41%）
   从外部印证了我们三组对比的结论——任何方案都要在误报和漏报之间选，
   没有免费的提升。

## 七、怎么复现本文的实测

```bash
# 1) 生成 4 分钟、第 120~123 秒含异常的测试视频
python scripts/make_long_video.py --duration 240 --event-at 120 --event-len 3

# 2) 默认 4 帧 —— 会漏掉异常，并且因重复帧产生一条置信度 1.0 的误报
python src/main.py analyze --input .cache/long_video/long_240s_event120.mp4 \
  --out reports/long_video_test

# 3) 抽 64 帧，确认第 33 帧（121.8s）落在异常上
python -c "
import sys; sys.path.insert(0,'.')
from pathlib import Path
from src.tools import VideoFrameExtractor
VideoFrameExtractor(max_frames=64).extract(
    Path('.cache/long_video/long_240s_event120.mp4'), Path('.cache/long_video/frames64'))
"
# 4) 单独分析命中的那一帧，验证模型本身没问题
python src/main.py analyze \
  --input .cache/long_video/frames64/long_240s_event120_frame_33.jpg \
  --out reports/long_video_test/hit_frame
```

`.cache/` 已在 `.gitignore` 中，生成的视频不会入库。
