# 团队分工方案（3 人）

> 课程要求：组内分工应覆盖**数据、模型、Agent、系统集成、评测**五个方面，
> 且**每位成员都应理解完整流程**。
> 3 人情况下把五个方面两两合并，每个人既有主责模块，也各有必须参与的公共任务。

---

## 一、分工总表

| | 成员 A | 成员 B | 成员 C |
| --- | --- | --- | --- |
| **角色** | 数据与评测负责人 | 模型与 Agent 负责人 | 系统集成与展示负责人 |
| **覆盖方向** | 数据 + 评测 | 模型 + Agent | 系统集成 +（协作评测） |
| **主责文件** | `data/`、`docs/数据说明.md`、`src/evaluate.py` | `src/llm.py`、`src/agents.py`、`src/toolkit.py` | `app/server.py`、`ui/index.html`、`src/pipeline.py` |
| **核心交付** | 数据集 + 标注 + 三组对比实验表 | 三 Agent 协作 + 自主工具调用 + 提示词调优 | 可操作界面 + 报告导出 + 版本管理 + 演示材料 |

---

## 二、逐人任务清单

### 成员 A — 数据与评测

**必须完成**

- [ ] 按 `docs/数据说明.md` 采集 ≥ 80 个独立样本（正常 ≥30 / 风险 ≥40 / 易混淆 ≥10）
- [ ] 完成人工标注，产出 `data/labels_dev.csv`、`data/labels_test.csv`
- [ ] 严格按规则划分 dev/test（同视频相邻帧不得跨集合）
- [ ] 维护易混淆样本清单，并在标注 `notes` 里写明混淆原因
- [ ] 跑三组对比实验：`python scripts/run_experiment.py ... --auto-evolve --rounds 2`
- [ ] 整理 `reports/experiments/comparison.md`，逐项核对 P / R / F1 / 误报率 / 漏报率 / 耗时 / 调用成本
- [ ] 汇总失败案例到 `docs/失败案例记录.md`

**加分项**

- [ ] 分析类别不均衡对指标的影响（哪些类样本少、Recall 为什么低）
- [ ] 统计弃权率，回答“证据不足时系统会不会硬报”

**验收标准**：任何人拿到 `data/` 目录和一条命令就能复现出报告里的每一个数字。

---

### 成员 B — 模型与 Agent

**必须完成**

- [ ] 接入多模态模型 API，跑通真实模式（`python src/main.py status` 显示 `api`）
- [ ] 调优三份提示词：感知 / 风险分析 / 证据复核（`configs/strategy_current.json`）
- [ ] 保证三个 Agent 都真正在做判断，而不是阈值过滤
- [ ] 验证 Agent 自主工具调用链路：工具清单进提示词 → Agent 申请 → 结果回灌 → 再判断
- [ ] 验证意见冲突处理：构造至少 1 个能触发分歧的样本，确认报告出现「冲突与仲裁」表格
- [ ] 跑消融实验（`--no-review` / `--no-rules` / `--no-memory` / `--no-agent-tools`），记录指标变化
- [ ] 完成两轮真实自进化（用开发集纠错，晋升 v0.3、v0.4），并记录 `change_log`

**加分项**

- [ ] 安装 `ultralytics` 启用 `detect_objects` 工具，比较开启/关闭对检测率的影响
- [ ] 做成本优化：精简提示词、减少不必要帧，比较模型调用次数的下降

**验收标准**：能对着一张从没见过的图，讲清每个 Agent 分别做了什么、依据是什么。

---

### 成员 C — 系统集成与展示

**必须完成**

- [ ] 保证 Web 界面可用：上传 → 分析 → 纠错 → 版本 → 报告下载全链路打通
- [ ] 确认界面能正确呈现：风险等级、证据、时间维度、Agent 执行过程、工具调用、冲突仲裁表
- [ ] 保证报告可导出（JSON + Markdown），且内容完整
- [ ] 维护版本管理流程：晋升 / 回退可用，`versions/` 记录完整
- [ ] 整理运行说明（`README.md`），保证换一台电脑能按说明跑起来
- [ ] 制作 8 分钟汇报 PPT（按 `docs/项目报告大纲.md` 第 8 章脚本）
- [ ] 录制系统演示视频（含备用录屏，防现场网络抖动）

**加分项**

- [ ] 把数字孪生/风险推演作为「后续计划」做一页概念图（不必实现，但能体现理解深度）
- [ ] 界面加入实验结果可视化（三组对比柱状图）

**验收标准**：在没参与开发的成员面前演示一遍，对方能独立跑通。

---

## 三、全员必须共同完成的事

- [ ] **每人理解完整流程**：能画出架构图，能讲清五类风险、三 Agent 分工、自进化闭环
- [ ] 每位成员至少完成 **1 次人工纠错**（轮流入库，让案例记忆有多来源样本）
- [ ] 每位成员至少撰写报告的一个完整章节
- [ ] 共同评审 `docs/失败案例记录.md`，确认分析属实
- [ ] 共同完成成员贡献表

---

## 四、节奏安排

| 阶段 | 目标 | 主要产出 | 责任重心 |
| --- | --- | --- | --- |
| 第 1 周 | 跑通真实模型，确认三 Agent 与工具调用可用 | 能对 5 张图给出稳定输出 | B 为主，C 配合界面 |
| 第 2 周 | 数据集就绪 | ≥80 样本 + 标注 + dev/test 划分 | A 为主 |
| 第 3 周 | 三组对比 + 两轮自进化 + 消融 | `comparison.md` + 版本记录 | A、B 共同 |
| 第 4 周 | 报告 + PPT + 演示视频 | 最终提交包 | C 为主，全员参与 |

---

## 五、协作约定

- 数据、策略、版本文件都入库，改动前先拉最新。
- 策略文件只通过 `promote` 命令更新，不要手工改 `strategy_current.json`（会破坏 change_log 追溯）。
- 每人提交前跑一遍 `python -m pytest tests -q`。
- 报告里的每个数字都必须能由某条命令复现，不能手写估计值。
