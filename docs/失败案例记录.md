## 第一部分：开发过程中发现的工程缺陷（已修复）

### 案例 E1：模拟结果被当成确认结论

| 项目 | 内容 |
| --- | --- |
| 现象 | 未配置 API Key 时，系统按文件名“猜”出的风险被标记为 `confirmed`（已确认），
而报告同一页的免责声明又写着“不能作为实际识别证据”——自相矛盾。 |
| 原因 | 复核阈值 `min_confidence=0.35`，而模拟结果的置信度是 0.42，恰好通过了复核。 |
| 危害 | 模拟数据会被误当成真实识别结论提交，属于可信度层面的严重问题。 |
| 修复 | 新增 `simulated` 状态；模拟模式下所有结论强制标记为 `simulated`，永不进入 `confirmed`；
复核阈值提高到 0.45。 |
| 验证 | `tests/test_safety_agent.py::test_pipeline_end_to_end_mock` 断言模拟结果不得为 `confirmed`。 |

**可写进报告的结论**：一个“看起来能跑”的系统，可能正在输出自相矛盾的结论。
可信度标注必须由代码强制保证，不能靠文档约定。

---

### 案例 E2：基础对照组永远拿不到结果

| 项目 | 内容 |
| --- | --- |
| 现象 | 三组对比实验里，「基础识别系统」的宏 F1 恒为 0.000，漏报率 0.778。 |
| 原因 | 模拟模型把“申请工具”的逻辑写在了所有任务分支上，连 `baseline` 任务也被当成需要先调工具，
于是第一轮返回空结果；而基础对照组按设计不执行工具循环，就永远停在空结果上。 |
| 修复 | 申请工具的逻辑限定为 `task == "perception"`；基础对照组不做工具调用。 |
| 验证 | 修复后基础对照组指标恢复正常。 |

**可写进报告的结论**：对照组看起来“很差”时，先怀疑对照组是不是坏了。
如果直接把这个 0.000 写进报告，会得出“多 Agent 提升巨大”的错误结论。

### 案例 E3：模型返回解析错误导致分析 Agent 静默失效

| 项目 | 内容 |
| --- | --- |
| 现象 | 风险分析 Agent 看起来在工作，实际上从未真正使用模型返回的结果，一律回退到规则默认等级。 |
| 原因 | 提示词里本身带了 JSON 输出示例。解析函数用“第一个 `{` 到最后一个 `}`”截取，
把提示词示例和真正的数据载荷粘成了一段非法 JSON，解析失败后被静默捕获。 |
| 修复 | 重写解析逻辑：优先取围栏块，其次扫出所有括号配平的顶层 JSON 对象，按**从后往前**的顺序尝试
（真正的载荷在文本末尾）。 |
| 验证 | `tests/test_safety_agent.py` 中 3 个 JSON 解析用例 + 冲突场景用例。 |

**可写进报告的结论**：最危险的 bug 是“不报错但没生效”。
凡是靠 `except` 兜底的链路，都必须有测试断言它确实做了事。

### 案例 E4：中文规则检索基本失效

| 项目 | 内容 |
| --- | --- |
| 现象 | 用「未戴护目镜」查询，检索不到任何规则。 |
| 原因 | 检索用空格切词，中文整句切不动，词元集合只有一个超长字符串，无法命中关键词表。 |
| 修复 | 加入字符二元组（bigram）相似度 + 关键词/别名子串匹配 + risk_type 直配的加权打分。 |
| 验证 | `test_retriever_hits_chinese_keyword`、`test_retriever_for_finding_prefers_exact_type`。 |

### 案例 E5：自进化版本号互相覆盖

| 项目 | 内容 |
| --- | --- |
| 现象 | 连续做两次纠错，两次都生成 `v0.2`，后一次把前一次覆盖掉，进化过程无法追溯。 |
| 原因 | 新版本号固定按“当前版本 +0.1”计算，而 `strategy_current.json` 一直没变。 |
| 修复 | 版本号改为扫描 `versions/` 目录取最大值再递增；同时把每轮“改了什么、依据什么”写入 `change_log`。 |
| 验证 | `test_version_increment_no_collision`：连续两轮必须得到 v0.3、v0.4。 |

**可写进报告的结论**：自进化如果没有可靠的版本管理，就无法回答“效果变差时回退到哪一版”。

### 案例 E6：视频中一闪而过的风险被当成确认风险

| 项目 | 内容 |
| --- | --- |
| 现象 | 4 帧里只有 1 帧出现的误检，被当成确认风险上报。 |
| 原因 | 逐帧独立分析后只做按风险类型去重，没有利用时间信息。 |
| 修复 | 加入跨帧时间融合：统计持续帧数与出现比例；单帧出现降置信度并降级为不确定，
多数帧持续出现则升置信度；同类风险跨帧合并为一条。 |
| 验证 | `test_temporal_fuse_downgrades_transient_hit`、`test_temporal_fuse_merges_duplicate_frames`。 |

### 案例 E7：图片格式不兼容导致 41.9% 的样本静默失败，指标全部失真

| 项目 | 内容 |
| --- | --- |
| 现象 | 第一次用真实模型跑 43 个测试样本，`base` 组有 **18 个样本（41.9%）** 的 `model_calls = 0`，
`findings` 为空，但 `duration_ms` 有 700~1200 ms。三组的 Macro F1 全是 0.000。 |
| 原因（两层） | ① **数据层**：Pexels 的 CDN 会按请求头里的 `Accept` 返回 **AVIF** 格式，而文件仍以 `.jpg`
落地。本地看图正常（Pillow 按内容识别），但智谱 GLM-4V 直接返回
`400 code 1210 图片输入格式/解析错误`。<br>② **代码层**：`agents.py` 的
`except Exception` 把调用失败转成 `{"findings": []}`，于是「模型没跑成」和
「画面确实没有风险」在报告里**长得一模一样**，pipeline 与 evaluate 都无法区分。 |
| 危害 | 这批失败样本会被当成「未发现风险」计入 —— 若真相是有风险，就是漏报被静默吞掉；
若真相是正常，则是白捡的准确率。真实案例：18 个失败样本里有 2 个标注是风险类，
直接让漏报率虚高且无法归因。**这一类 bug 比模型判错更危险，因为它伪装成「系统很保守」。** |
| 修复 | ① 新增 `scripts/normalize_images.py`：统一转真 JPEG、剥除 EXIF、最长边限制 1280；
`fetch_web_images.py` 的 `Accept` 头去掉 `image/avif`，从源头避免。<br>
② `AgentTrace` 增加 `error` 字段，`AnalysisReport` 增加 `analysis_errors`；
失败时轨迹写明「感知步骤失败，本帧结果不可用」。<br>
③ `evaluate.py` 把失败样本**单独统计并排除出 P/R/误报/漏报**，对比表新增「分析失败」列，
`comparison.json` 里保留 `failed_sample_ids`。 |
| 验证 | 同一张曾失败的图（`10419527.jpg`）转码后单跑：`模型调用 1 次｜耗时 2993 ms`，
风险条目 1 条，恢复正常。全部 55 项单元测试通过。 |

**可写进报告的结论**：做对比实验前，必须先证明「每个样本都真的跑过了」。
一个静默吞掉异常的 `except`，足以让整张结果表失去意义 —— 而且它不会报错、不会崩，
只会给你一个漂亮的 0.000。**「无输出」和「无风险」必须在数据结构上分开。**

### 案例 E8：公开图库里根本没有「违规现场」，数据集只能两路拼

| 项目 | 内容 |
| --- | --- |
| 现象 | 按 10 个查询词从 Pexels 采集了 108 张候选图，人工逐张阅图后**只有 35 张是真实实验室画面**，
其余 73 张全部因题材跑偏被剔除（跑偏率 **67.6%**）。 |
| 具体跑偏 | `coffee cup desk` → 全部是咖啡店拉花特写；`wet floor` → 浴室地砖、木地板、地毯；
`cluttered floor boxes` → 办公桌杂物、狗、邮票；`laboratory equipment` → 医用注射器、
手术器械、医院病房；`safety goggles` → 眼镜店太阳镜货架。 |
| 原因 | 「试剂瓶没贴标签」「实验台上摆着咖啡杯」「地面洒了一滩液体还没处理」这些画面，
现实中没人会专门去拍并上传图库 —— 图库里的实验室图都是**宣传照**，天生是规范场景。 |
| 应对 | 违规场景改用文生图构造（49 张），并在 `data/synth/synth_manifest.json` 里逐张记录
提示词与截断水印的操作；报告中明确标注「合成，非实拍」，不得与 35 张真实照片混为一谈。 |
| 遗留风险 | 合成图的光照、构图、噪点分布与真实手机照片不同，模型可能在合成图上表现更好；
换成组员实拍后必须**重跑全部实验**，不能沿用本次数字。 |

**可写进报告的结论**：数据获取的难点不在「找 80 张图」，而在「找到真实存在的违规画面」。
这个约束直接决定了技术路线 —— 也是为什么最终数据集是 35 张真实 + 49 张合成的混合体，
而不是一个看起来更整齐的纯真实数据集。

## 第二部分：模型判断失败案例（待用真实数据填写）


> 用真实模型跑完测试集后，从误报 / 漏报样本中挑 ≥5 条填入下表。
> 数据来源：`reports/experiments/*/..._report.json` 与 `comparison.md` 的混淆对统计。
> **不要美化**。课程明确说明“改进没有提升也可以，但须如实分析原因”。

### 模板

```markdown
### 案例 M-01：<一句话概括>

| 项目 | 内容 |
| --- | --- |
| 样本 | `data/test/xxx.jpg`（sample_id: xxx） |
| 标注真值 | risk_type=xxx, severity=xxx |
| 系统输出 | 风险类型 / 等级 / 状态 / 置信度 |
| 失败类型 | 误报 / 漏报 / 等级判错 / 应弃权却硬报 |
| 原因分析 | 从画面特征、提示词、规则覆盖三个角度分析 |
| 是否已修正 | 通过第几轮自进化、具体改了什么、复测结果如何 |
```

### 预期会出现的高频失败模式（采集样本时请重点覆盖）

| 编号 | 预期失败模式 | 观察点 |
| --- | --- | --- |
| M-01 | 透明水杯 / 洗瓶被误判为 PPE 缺失或饮食风险 | 误报率是否集中在 `food_or_drink` 与 `ppe_missing` 之间 |
| M-02 | 拍摄角度或头发遮挡导致护目镜被误判缺失 | 系统是否会正确输出 `uncertain` 而不是硬报 |
| M-03 | 已断电冷却的加热设备被判为工作中热源 | `flammable_near_heat` 的误报情况 |
| M-04 | 地面反光 / 阴影被判为液体洒漏 | 视频场景下是否会因跨帧融合被过滤掉 |
| M-05 | 标签被遮挡的试剂瓶被判为标签缺失 | 证据复核 Agent 能否拦下 |
| M-06 | 画面正常但人员背对镜头，系统过度推断 | 正常样本上的误报率 |
| M-07 | 真实风险因画面太远 / 太小而漏报 | 漏报率与风险位置的相关性 |

## 附：如何快速定位失败案例

```bash
# 1. 生成测试集报告
python scripts/run_experiment.py --labels data/labels_test.csv --groups multi

# 2. 看混淆对与分类别指标
python src/main.py evaluate --labels data/labels_test.csv \
  --reports reports/experiments/multi --out-md reports/eval_multi.md

# 3. 找出被误报的样本（报告里 status=confirmed 但标注是 normal）
#    然后在 reports/experiments/multi/ 下打开对应 *_report.md 看证据描述
```

**记录要求**：每条案例都要能回答“为什么错”和“改了之后是否有改善”，
只写“模型能力不足”不算分析。
