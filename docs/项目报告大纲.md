- 1.2 为什么聚焦高校化学/材料实验室（数据可合法获取、风险类型清晰、可闭环验证）。

- 1.4 功能需求清单（逐条对应课程参考任务 1~6）。

**评分点**：需求是否落到“可通过数据判断”的可执行定义，而不是抽象口号。

## 第 2 章 系统架构与工程实现（对应：工程实现）

- 2.1 总体架构图（预抽取 → 三 Agent → 时间融合 → 报告 → 反馈闭环）。
  - 材料：`README.md` 第四节架构图，可直接改用。
- 2.2 模块划分与职责：`pipeline / agents / toolkit / tools / llm / self_evolution / evaluate`。
- 2.3 数据存储设计：策略 `configs/`、版本 `versions/`、案例 `memory/`、日志 `reports/tool_calls.jsonl`。
- 2.4 降级设计：无 API Key 自动切模拟模式；模型调用失败回退阈值复核；单个工具不可用不影响主流程。
- 2.5 测试：`python -m pytest tests -q`，列出覆盖点与用例数。
  - 材料：`tests/test_safety_agent.py`。

**可写亮点**：仅用 Python 标准库即可跑通完整流程（零依赖可演示）；
工具调用失败、模型返回非法 JSON、视频缺 OpenCV 等异常路径都有兜底。

## 第 3 章 Agent 协作与自主决策（对应：Agent 协作与自主决策，25 分）

- 3.1 三个 Agent 的角色、输入、输出（表格）。
  - 材料：`README.md` 第四节表格。
- 3.2 协作流程时序：谁先跑、谁消费谁的输出、如何形成最终结论。
- 3.3 **自主工具调用**：
  - 工具清单以提示词形式交给 Agent，由 Agent 自己决定调什么；
  - 工具执行结果回灌，形成“观察 → 决策 → 调工具 → 再观察”闭环；
  - 上限 2 轮，防模型刷调用；
  - 全部调用落 `reports/tool_calls.jsonl`。
  - 材料：`src/toolkit.py`、报告中「Agent 执行过程」一节的工具调用记录。
- 3.4 **意见不一致的处理**（课程明确要求）：
  - 复核 Agent 是质疑者，不附和；
  - 三类分歧（rejected / uncertain / confirmed 但与原判不符）各自如何记录；
  - 仲裁规则：保守优先 + 高风险分歧进入「需人工优先复核」；
  - 报告单列「Agent 意见冲突与仲裁」表格。
  - 材料：`src/agents.py::EvidenceReviewAgent`、任一份含冲突的报告。
- 3.5 消融验证：关闭复核 Agent 后误报率的变化（填第 4 章数据）。

**评分点**：Agent 是不是真的在做决策，而不是「串起来的三个函数调用」。

## 第 4 章 实验与结果（对应：自进化与实验验证，25 分）

- 4.1 数据集：来源、规模、类别分布、标注方式、dev/test 划分（引用 `docs/数据说明.md`）。
  - 必须写清：同一视频的相邻帧未跨集合；测试集未用于进化。
- 4.2 三组对比：
  | 实验组 | 说明 | Macro P | Macro R | Macro F1 | 误报样本率 | 漏报样本率 | 平均耗时 | 平均模型调用 |
  | --- | --- | --- | --- | --- | --- | --- | --- | --- |
  | 基础识别系统 | 单模型直出，无 Agent / 工具 / 规则 | | | | | | | |
  | 多 Agent + 工具调用 | 本系统 | | | | | | | |
  | 两轮自进化后 | 同上 + 两轮策略更新 | | | | | | | |
  - 材料：`reports/experiments/comparison.md`（脚本自动生成，直接粘贴）。
- 4.3 消融实验：关闭复核 Agent / 关闭规则检索 / 关闭案例记忆 / 关闭自主工具调用，各一项。
  - 材料：`python src/main.py analyze --no-review` 等 + `evaluate` 对比。
- 4.4 成本分析：平均耗时、平均模型调用次数、平均工具调用次数。
- 4.5 **如实分析**：如果某项改进没有提升甚至变差，写清原因（课程明确允许“没有提升”，但要求如实分析）。
  常见原因：样本量不足、模拟数据、提示词改动引入新偏差、案例记忆污染等。
- 4.6 弃权率：证据不足时系统是否正确输出 `uncertain` 而不是硬报。

**评分点**：数字完整（P/R/误报/漏报/时间/成本都要有）+ 消融 + 如实分析。

## 第 5 章 自进化机制（对应：自进化与实验验证）

- 5.1 为什么采用**人工确认式**自进化（而不是让模型随便改自己）。
- 5.2 闭环流程六步：纠错 → 入库 → 聚合 → Agent 提案 → 组员确认 → 复测/回退。
- 5.3 三种修改载体：易混淆说明 / 提示词补丁 / 新增规则，各举一例真实改动。
  - 材料：`versions/strategy_v0.*.json` 的 `change_log`（含 `diagnosis` 与 `evidence`）。
- 5.4 版本管理：版本号递增防撞车、`change_log` 记录依据、晋升与回退命令。
- 5.5 两轮进化的实际效果对比（接 4.2 的第三行）。

**评分点**：必须是**具体策略更新 + 效果验证**；“让模型再想想”不算。

## 第 6 章 失败案例与局限性

- 6.1 典型失败案例（≥5 条，引用 `docs/失败案例记录.md`）：
  每个案例写：输入 → 系统输出 → 正确答案 → 原因分析 → 是否已通过自进化修正。
- 6.2 系统局限：
  - 依赖多模态模型自身能力，模型换版本会导致结果漂移；
  - 规则库覆盖有限，未收录的情形一律输出 `uncertain`；
  - 视频时间融合是决策层融合，未做目标级跟踪；
  - 单帧图像无法判断动态风险（如“人员正在靠近热源”）；
  - 模拟模式不能用于任何结论。
- 6.3 后续计划：目标检测接入、目标级跟踪、成本优化、扩展到更多场景。
