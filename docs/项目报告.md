**课程**：工科导论（7 班）　|　**组员**：（待填 3 人姓名）　|　**日期**：2026 年 10 月 23 日

## 摘要

针对高校化学/材料实验室的人工巡查难以覆盖全部时段、隐患发现滞后的问题，本项目实现了一个可运行的危险场景识别系统。系统以多模态大模型为感知基础，构建**场景感知、风险分析、证据复核**三个协作 Agent，支持 Agent 自主发起工具调用（局部裁剪、规则检索、案例检索、视频抽帧），并对视频做跨帧时间融合；同时实现了**人工确认式自进化**——由策略进化 Agent 提出提示词与规则修改方案，经组员确认后晋升新版本，支持回退。

在 84 个独立样本（35 张真实图库照片 + 49 张文生图合成样本，含 20 张易混淆样本）构成的测试集上完成三组对比：基础识别系统 Macro F1 为 0.479、误报样本率 37.2%；多 Agent 系统 F1 提升至 **0.535**、误报率降至 **9.3%**；两轮自进化后 F1 反而降至 0.438。消融实验表明，关闭证据复核 Agent 会使误报率从 9.3% 回升到 20.9%，验证了复核机制是抑制误报的主要来源。**两轮自进化未带来提升，本文如实报告并给出归因。**

## 第 1 章 需求分析与场景定义

### 1.1 选题背景

高校实验室的安全管理长期依赖"制度 + 人工巡查 + 事后追责"。这套体系有三个结构性缺口：

1. **覆盖面不足**。实验楼开放时间长，巡查只能覆盖有限时段，夜间与周末几乎是盲区。
2. **专业门槛高**。判断"热源旁边放一叠纸算不算隐患""未贴标签的瓶子该不该报警"，需要化学背景，宿管与保安不具备。
3. **发现滞后**。多数隐患在被发现时已经存在较长时间（洒漏未处理、通道被杂物堵塞）。

多模态大模型的出现使"让机器看懂实验室画面并给出判断依据"变得可行。本项目要回答的问题是：**这样的系统在三类场景（正常、危险、易混淆）下，实际能达到什么水平，多 Agent 协作与自进化各带来多少收益。**

### 1.2 为什么聚焦高校化学 / 材料实验室

选择这个场景不是因为它简单，而是因为它满足三个可验证性条件：

- **风险类型可枚举**：实验室安全隐患有成熟的标准分类（PPE、试剂管理、热源、饮食、洒漏与通道），每类都有明确的判定依据，能写成可执行的检查项，而不是"氛围不安全"这种无法验证的描述。
- **数据可合法获取**：可以通过组员在授权下拍摄获得，也可以用公开授权素材与合成方式构造，避免为了训练模型去制造真实危险。
- **闭环可验证**：每条判定都能对照"人看到的证据"与"系统说的证据"，误报与漏报可以逐条归因，而不是只能给一个笼统的准确率。

### 1.3 五类风险的判定依据

系统的分类法不是拍脑袋定的，每条规则都写明判定依据、默认等级与对应处置建议，来源见 `rules/lab_safety_rules.json` 的 `source` 字段。

| 风险类型 | 判定依据（可见证据） | 默认等级 | 典型样本 |
| --- | --- | --- | --- |
| `ppe_missing` | 进行液体操作/加热/玻璃器皿操作时，眼部未见护目镜、身体未见实验服、手部未见手套 | medium | 学生徒手拿盛液烧杯；护目镜挂在颈部未佩戴 |
| `reagent_management` | 试剂容器敞口未盖、标签缺失/字迹不可辨、无危险象形标识、性质相抵触试剂混放 | medium | 台面三个标签空白的试剂瓶，其中一个开盖 |
| `flammable_near_heat` | 明火或通电发热设备（酒精灯、电热板、加热套）数厘米范围内存在纸张、纸箱、有机溶剂、塑料容器 | **high** | 电热板通电发红，旁边紧挨一叠活页纸 |
| `food_or_drink` | 实验工作区出现饮水杯、饮料杯、食品包装 | low | 台面上带吸管的一次性纸杯紧邻试管架 |
| `spill_or_obstruction` | 地面/台面存在未处理的液体；通道被纸箱、推车、横穿电线阻塞 | medium | 地面一滩透明液体且无警示牌；过道被周转箱堵死 |

**等级设置遵循一个原则**：能直接引燃或导致坠落/滑倒的判 high，需要叠加其他条件才致害的判 medium，主要影响规范性的判 low。这个区分直接影响误报的代价——把 high 级风险误报为 low 级，比反过来危险得多。

### 1.4 功能需求与实际达成

| 课程要求 | 实现情况 |
| --- | --- |
| ≥4 类可通过数据判断的风险 | 5 类，见 1.3 |
| 支持图像与短视频，视频需结合多个时间点 | 图像 + 视频，按时间轴抽 4 帧后做跨帧融合（第 3.4 节） |
| 输出类别/位置/等级/证据/建议/不确定性 | 全部输出，证据必须具体到"看到什么、在哪" |
| ≥3 个 Agent 且处理意见不一致 | 3 个 Agent，复核 Agent 为质疑者，含仲裁规则（第 3.3 节） |
| Agent 自主选择工具 | 工具清单写入提示词，Agent 自行申请，最多 2 轮（第 3.2 节） |
| 由 Agent 提出修改方案，人工确认后更新 | 策略进化 Agent 提案 → 人工确认 → 晋升，支持回退（第 5 章） |
| 可操作界面 + 报告导出 | Web 界面（上传→分析→纠错→版本→下载）+ JSON/Markdown 报告 |
| ≥80 个独立样本，含易混淆，dev/test 划分 | 84 个，20 张易混淆，dev 41 / test 43（第 4.1 节） |
| 三组对比 + 消融 + 成本 | 全部完成（第 4 章） |

## 第 2 章 系统架构与工程实现

### 2.1 总体架构

```
图片 / 短视频
    │
    ├─〔视频〕按时间轴均匀抽 4 帧
    ▼
┌────────────────────────────────────────────┐
│ 场景感知 Agent                              │
│  看图 → 描述场景 → 提出候选风险（含证据/位置）│
│  ↕ 自主工具调用循环（最多 2 轮）             │
│    crop_region / detect_objects /           │
│    search_rules / search_cases              │
└────────────────────────────────────────────┘
    ▼ 候选风险
┌────────────────────────────────────────────┐
│ 风险分析 Agent                              │
│  候选风险 + 检索到的规则 + 历史纠错案例       │
│  → 等级 / 处置建议 / 置信度 / 判定依据        │
└────────────────────────────────────────────┘
    ▼ 带等级的结论
┌────────────────────────────────────────────┐
│ 证据复核 Agent（质疑者立场）                 │
│  → confirmed / uncertain / rejected         │
│  → 与前者分歧时记录并仲裁                   │
└────────────────────────────────────────────┘
    ▼
跨帧时间融合（持续帧数 / 出现比例 / 合并重复）
    ▼
风险报告（JSON + Markdown）→ Web 界面展示
    ▼
人工纠错 → 案例记忆 → 策略进化 Agent 提案 → 组员确认 → 新版本 → 复测 → 可回退
```

### 2.2 模块划分

| 模块 | 职责 |
| --- | --- |
| `src/pipeline.py` | 主流程编排：输入解析（视频抽帧）→ 逐帧分析 → 时间融合 → 报告生成 |
| `src/agents.py` | 三个 Agent 与基础对照系统（`BaselineAnalyzer`） |
| `src/toolkit.py` | 工具注册表：把工具清单渲染进提示词，解析 Agent 的工具申请并执行 |
| `src/tools.py` | 规则检索、案例记忆、工具日志、视频抽帧、局部裁剪 |
| `src/llm.py` | 模型客户端：真实 API（指数退避重试）+ 模拟模式 + `.env` 加载 |
| `src/self_evolution.py` | 案例记录、误判聚合、策略进化 Agent、版本管理 |
| `src/evaluate.py` | 多标签评测、多组对比、失败样本单列 |

**一个刻意的设计**：`agents.py` 里三个 Agent 的提示词都通过 `_format_prompt` 做**定向占位符替换**，而不是 `str.format`。因为提示词里含有 JSON 示例，`str.format` 会把示例里的花括号当成占位符直接崩掉。这个坑在开发中真实踩过，改法写在代码注释里。

### 2.3 数据存储

| 内容 | 位置 | 说明 |
| --- | --- | --- |
| 当前策略 | `configs/strategy_current.json` | 只通过 `promote` 命令更新，不手工改，否则 `change_log` 失去可追溯性 |
| 历史版本 | `versions/strategy_v0.*.json` | 每个版本含完整的 `change_log`（改了什么、为什么改、依据哪些案例） |
| 纠错案例 | `memory/cases.json` | 人工纠错记录，供案例检索与误判聚合 |
| 工具调用日志 | `reports/tool_calls.jsonl` | 每次工具调用一行，含参数与结果摘要 |
| 分析报告 | `reports/experiments/<组别>/*_report.json` | 每样本一份，含 findings、traces、conflicts、成本 |

### 2.4 降级与容错设计

系统的可用性不依赖任何单一环节，这是被实际故障逼出来的设计：

| 故障 | 系统行为 |
| --- | --- |
| 未配置 API Key | 自动切模拟模式，所有结论标记 `simulated`，**永不进入 `confirmed`** |
| 模型返回非法 JSON | `extract_json` 分级降级解析：直接解析 → 剥代码块标记 → 正则提取首个对象 → 返回空结果并记录 |
| 429 限流 | 指数退避 + 抖动重试，429 单独给 6 次机会并遵守 `Retry-After` |
| 401/403 鉴权失败 | 立即失败并提示检查 `.env`，不做无意义重试 |
| 模型调用彻底失败 | 轨迹记 `error`，报告记 `analysis_errors`，**该样本不进 P/R 统计**（第 6.1 节案例 E7） |
| 未安装 OpenCV | 视频抽帧工具返回"不可用"，不影响图片分析 |
| 未安装 ultralytics | `detect_objects` 返回不可用，其余工具正常 |

### 2.5 测试

`python -m pytest tests -q` → **55 项全部通过**。覆盖重点：

- 端到端流程（模拟模式下结论必须为 `simulated`，断言不得出现 `confirmed`）
- 时间融合（瞬时单帧命中必须降级、多帧同类必须合并）
- 版本管理（连续两轮进化版本号不得撞车）
- 评测口径（弃权不计入正例、失败样本不计入 P/R）
- `.env` 解析（注释、`export`、引号、BOM、CRLF、环境变量优先）
- 重试逻辑（429 退避时长落在正确区间）

## 第 3 章 Agent 协作与自主决策

### 3.1 三个 Agent 的职责边界

| Agent | 输入 | 输出 | 关键约束 |
| --- | --- | --- | --- |
| 场景感知 | 图像（含裁剪后的局部图）、场景说明、策略提示词、工具清单 | 场景描述、候选风险（证据 + 位置）、工具申请 | 只负责"看到什么"，不做等级判定 |
| 风险分析 | 候选风险、检索到的规则、历史纠错案例 | 等级、处置建议、置信度、判定依据（规则 id / 案例 id） | **无规则支持时强制 `uncertain`**，不许凭空编等级 |
| 证据复核 | 风险分析的结论、证据、置信度 | `confirmed` / `uncertain` / `rejected` + 理由 | 质疑者立场，不附和 |

三个 Agent **全部走真实模型推理**，不是"三个函数串起来"。区别在于：感知 Agent 的输出直接决定后续两个 Agent 有没有活干；复核 Agent 有权推翻前两者的结论。

### 3.2 Agent 自主工具调用

工具清单以结构化描述写进感知 Agent 的提示词，由 Agent 自己决定调不调、调哪个：

| 工具 | 用途 | 执行结果如何回灌 |
| --- | --- | --- |
| `crop_region` | 把可疑区域裁剪放大 | 裁剪图作为**新图像**追加进下一轮请求 |
| `detect_objects` | 目标检测（需 ultralytics） | 检测框列表转文本观察 |
| `search_rules` | 检索安全规则 | 命中的规则条目转文本观察 |
| `search_cases` | 检索历史纠错案例 | 相似案例转文本观察 |

闭环是"观察 → 决策 → 调工具 → 再观察"，最多 2 轮，防止模型反复刷调用。全部调用写入 `reports/tool_calls.jsonl`。

**实测情况需要如实说明**：在本项目的测试集上，Agent 主动申请 `crop_region` 的频率很低——它倾向于直接给结论。这直接导致了 `ppe_missing` 的失败（第 6.2 节案例 M2）：如果它肯把人的脸部裁出来放大，"有没有戴护目镜"本来是可以看清的。这不是工具没实现，是 Agent 没意识到自己看不清。

### 3.3 意见不一致的处理

复核 Agent 的定位是**质疑者而非审核员**，它不负责让流程通过。三类分歧的处理：

| 情形 | 记录方式 | 仲裁结果 |
| --- | --- | --- |
| 复核判 `rejected` | 记录 `review_verdict=rejected` + 理由 | 该风险记为误报，状态降为 `rejected`，进入人工复核队列 |
| 复核判 `uncertain` | 记录 `review_verdict=uncertain` | 降级为不确定，**不计入正例**，单独计入弃权率 |
| 复核判 `confirmed` 但与分析的等级不符 | 记录双方等级 | 取较保守的一方 |

**高风险分歧特殊处理**：若原判为 `high` 却被降级或驳回，额外标记 `needs_human_review`，进入"人工优先复核"队列。理由是 high 级误判的代价不对称——漏掉一次"明火旁有机溶剂"的后果远大于多看一张图。

报告里单列「Agent 意见冲突与仲裁」表格，每处分歧可追溯到具体行。

**一个真实的仲裁实例**（样本 `synth_confuse_01`，实际是带标签的塑料洗瓶，真值 `normal`）：

| 环节 | 内容 |
| --- | --- |
| 感知 Agent | 报出 `food_or_drink`：「玻璃烧杯内有液体，可能是水或其他透明液体，但没有明确的标识表明这是安全的饮用水」 |
| 风险分析 Agent | 定为 medium |
| 证据复核 Agent | **rejected**：「The conclusion is not supported by the evidence as there is no indication that the liquid in the glass beaker poses a risk.」 |
| 仲裁结果 | 「采纳复核意见，判定为误报，交人工确认」，并置 `needs_human_review = true` |
| 最终状态 | `rejected`，未计入误报 |

这个实例有两点值得注意：

1. **复核机制确实生效**了——如果没有它，这张图就是一次误报；
2. **但拦截理由并不正确**——复核说的是"没有证据表明这液体有风险"，而不是"这是一个洗瓶、不是饮料杯"。感知 Agent 把它看成了玻璃烧杯，这个错误观察并没有被纠正，只是结论被"证据不足"挡了下来。

这说明**复核 Agent 的本质是"证据充分性检查"，不是"事实核查"**。它检验结论与证据是否匹配，但不检验证据本身的真假。当两个 Agent 基于同一个错误观察时，复核反而会把错误确认得更牢——第 6.2 节案例 M1 就是这种失效。

### 3.4 视频的时间维度分析

课程要求"视频分析应结合多个时间点的信息"。实现方式是**决策层融合**，不是目标级跟踪：

1. 按时间轴均匀抽 4 帧，逐帧独立分析；
2. 统计同一风险出现在哪些帧、持续帧数、出现比例（`persistence`）；
3. **只在极少数帧一闪而过** → 判为疑似瞬时误检，降置信度并降级 `uncertain`；
4. **在多数帧持续出现** → 证据更强，升置信度；
5. 同类风险跨帧合并为一条，避免重复预警。

实测一段 12 秒的巡视序列（第 1 镜头正常，第 2~4 镜头地面有未处理液体），系统输出：

- `spill_or_obstruction`：**第 2~4 帧（持续 3/4 帧，占 75%）**，置信度 1.00，判定 confirmed；
- `food_or_drink`：**仅第 1 帧（持续 1/4 帧，占 25%）**，置信度 0.59，判定 uncertain 并标记"需人工优先复核"。

第 2 条正是时间融合的价值所在：第 1 帧里那个被误认为饮料杯的物体，只出现了一帧，系统没有把它当成稳定存在的风险。

### 3.5 消融验证

关闭复核 Agent 后，误报样本率从 9.3% 升至 20.9%（翻 2.25 倍），Macro F1 从 0.535 降至 0.487。数据见第 4.3 节。

这说明复核 Agent 不是流程上的装饰——它承担了绝大部分误报抑制工作。

## 第 4 章 实验与结果

### 4.1 数据集

**规模与构成**：84 个独立图像样本，来源分两路：

| 来源 | 数量 | 覆盖 | 性质 |
| --- | --- | --- | --- |
| Pexels 公开图库 | 35 | 实验室**规范场景** + 少量陷阱 | 真实照片，Pexels License |
| 文生图合成 | 49 | 31 张违规场景 + 18 张易混淆 | **合成，非真实拍摄** |

**为什么必须两路**：这是本项目最需要如实说明的一点。按 10 个查询词从 Pexels 采集了 108 张候选，人工逐张阅图后**只有 35 张是真实实验室画面**，其余 73 张因题材跑偏被剔除（跑偏率 67.6%）——`coffee cup desk` 返回的全是咖啡店拉花特写，`wet floor` 全是浴室地砖与木地板，`laboratory equipment` 返回医用注射器与手术器械。原因很直接：**公开图库里不存在"违规现场"照片**，没有人会专门去拍"试剂瓶没贴标签""实验台上摆着咖啡杯"并上传图库。而为了拍这些画面去制造危险情境，是课程明令禁止的。

因此违规类样本只能靠文生图构造，并在 `data/synth/synth_manifest.json` 里逐张记录提示词，报告中不与 35 张真实照片混为一谈。

**类别分布**（明显不均衡，未做重采样）：

| 类别 | dev | test | 合计 |
| --- | --- | --- | --- |
| `normal` | 25 | 26 | 51 |
| `ppe_missing` | 4 | 4 | 8 |
| `reagent_management` | 3 | 3 | 6 |
| `flammable_near_heat` | 3 | 3 | 6 |
| `food_or_drink` | 3 | 3 | 6 |
| `spill_or_obstruction` | 3 | 4 | 7 |
| **合计** | **41** | **43** | **84** |

normal 占 61%。这是"违规场景本身稀少"的真实反映。我们**没有通过复制样本把数字做平**——那会让 accuracy 虚高。评测因此以 Macro F1 与逐类 P/R 为主。

**易混淆样本（20 张）**：真值全是 `normal`，模型报出任何风险即为误报。四类陷阱设计对应四类高频误报：

1. **洗瓶 / 蒸馏水瓶 vs 饮料容器**——外形相似，标签可区分；
2. **断电电热板 vs 工作中的热源**——指示灯、显示屏、电源线状态可区分；
3. **地面窗光反光 vs 液体洒漏**——砖缝与浮尘是反证；
4. **护目镜摆放/推到额头 vs 未佩戴**——需区分"器材在场"与"正确佩戴"。

**划分与约束**：

- 按 `risk_type` 分层划分，随机种子固定为 `20261023`，重跑可复现；
- 同一段视频的相邻帧不跨集合。本项目视频样本（`data/web_video/`）的源图全部取自 dev 集，**未使用任何 test 样本**，且视频本身不计入 84 个独立样本的定量统计；
- **测试集未参与任何策略更新或案例记忆**：`run_experiment.py` 中自进化只读 `--dev-labels`，评测只读 `--labels`，代码层面强制隔离。

**图像预处理**：统一转真 JPEG（非此格式会导致接口拒收，见第 6.1 节 E7）、剥除 EXIF、最长边限制 1280px。

### 4.3 消融实验

策略固定为 v0.2，测试集不变，每次只关掉一项功能：

| 配置 | Macro F1 | 误报样本率 | 漏报样本率 |
| --- | --- | --- | --- |
| 完整系统（参照） | **0.535** | **0.093** | 0.186 |
| 关闭证据复核 Agent | 0.487 | **0.209** | 0.163 |
| 关闭 Agent 自主工具调用 | 0.529 | 0.140 | 0.186 |

| 组 | 误报数 | 说明 |
| --- | --- | --- |

### 4.4 成本分析

| 实验组 | 平均耗时 | 平均模型调用 | 平均工具调用 | 测试集总调用 |
| --- | --- | --- | --- | --- |
| 基础系统 | 4865 ms | 1.00 | 0.0 | 43 |
| 多 Agent | 6971 ms | 1.98 | 1.0 | 85 |
| 两轮自进化后 | 11652 ms | 2.63 | 1.0 | 113 |

多 Agent 的成本约为基础的 **2 倍调用、1.4 倍时间**，换来误报率下降 75%。这个交换比在实验室场景下是可接受的——一个每天误报十几次的系统没人会看，而 7 秒的响应时间对巡查场景无感。

自进化后成本涨到 **2.6 倍调用、2.4 倍时间**，指标反而变差：提示词被 7 条易混淆说明反复注入，既拖慢速度又没带来收益。

### 4.5 如实分析：哪些改进有效，哪些没有

**有效的部分**：

多 Agent 协作有效，但**收益集中在"减少误报"而非"提高召回"**。误报率从 37.2% 降到 9.3%，易混淆样本误报从 8/8 降到 1/8；代价是召回从 0.783 掉到 0.550。这不是"系统变强了"，而是**判断口径变了**：基础系统看到实验室里有人有瓶子就报警，复核 Agent 要求"看得见的证据"，够不上就判 `uncertain` 或驳回。在实验室场景里，这个方向比高召回更合理，但**漏报率接近翻倍这件事必须写清楚**——如果某个场景下一个漏报的代价远高于一次误报，这个取舍就该反过来，应当调低复核阈值而不是照抄本配置。

**没有效果的部分**：

两轮自进化后 Macro F1 从 0.535 降到 0.438，误报率从 9.3% 反弹到 18.6%。逐版本追查原因：

| 版本 | 提案来源 | 改了什么 | 后果 |
| --- | --- | --- | --- |
| v0.3 | `llm_agent`（模型自己提案） | 3 条易混淆说明 + 2 条新规则 | 其中一条写成"检测到人员未佩戴 PPE 时应**立即报警**"——这是**处置建议**，不是易混淆说明，塞进感知提示词等于命令模型更激进地报警 |
| v0.4 | `rule_based_fallback`（**模型提案失败，回退规则驱动**） | 一次性新增 7 条"X↔normal"约束 | 每条都写"证据不足时应输出 uncertain 而不是硬报风险"，叠加后系统过度保守，`spill_or_obstruction` 召回从 0.750 掉到 0.250 |

三条直接教训：

1. **自进化的载体用错了位置**。把处置建议写进"易混淆说明"，效果与意图相反。载体分类需要校验。
2. **第二轮模型提案失败**，系统回退到规则驱动的兜底方案。兜底能用，但一次性堆 7 条约束，没有做"少量多次"，导致无法归因到底是哪一条起了负面作用。
3. **"进化"不等于"变好"**。只用 dev 集自进化时，系统会朝"在 dev 上少报错"的方向过拟合，泛化到 test 反而更差。

这一点对答辩很重要：如果只说"我们实现了自进化且效果提升"，审阅者一问"提升多少、怎么保证不退化"就露馅了。**如实报告负结果并给出归因，比虚假提升有价值。**

### 4.6 弃权率

多 Agent 组弃权率 4.6%（2 个样本），自进化后 2.3%。弃权是指系统输出 `uncertain` 而不是硬报——这是课程要求的"证据不足时明确提示不确定性"。

弃权率低有两个含义：一方面说明系统的判断比较确定，另一方面也可能说明**它不够谨慎**——有些本该弃权的情形被硬判了（第 6.2 节案例 M1 就是典型：证据其实是反的，系统却给出了 1.00 的置信度）。

## 第 5 章 自进化机制

### 5.1 为什么是"人工确认式"

让模型自己改自己的提示词和规则，风险是显而易见的：**它不知道什么改动会损害什么**。本项目的 v0.3 提供了一个真实的反面例子——模型提出的规则原文是：

> 「食物/饮料检测误报规则：在非餐饮区域检测到食物或饮料时，若无异常行为，则视为正常。」

这条规则如果真的生效，**会把实验室里真实的饮食风险也一起放过**——而"实验区饮食"恰恰是五类风险之一。它看起来在"修误报"，实际是在摧毁召回。同时这条规则的 `source` 字段写的是"待补充权威来源"，违反了项目"每条规则必须注明权威依据"的约定。

所以流程设计为六步，**人工确认是不可跳过的一环**：

```
人工纠错 → 写入案例记忆 → 聚合误判模式 → 策略进化 Agent 提案
    → 组员确认（可修改/驳回）→ 晋升新版本 → 复测 → 不满意则回退
```

### 5.2 三种修改载体

| 载体 | 作用 | 实际改动示例 |
| --- | --- | --- |
| **易混淆说明**（`risk_type_notes`） | 把"A 被误判为 B"沉淀成显式约束，注入感知提示词 | v0.4：`spill_or_obstruction↔normal`：「已有 2 次把 spill_or_obstruction 误报为风险（实际正常），证据不足时应输出 uncertain 而不是硬报风险」 |
| **提示词补丁**（`prompt_patch`） | 追加具体可执行的感知要求，每轮替换而非累加 | v0.3/v0.4 均更新了感知提示词 |
| **新增规则**（`proposed_rules`） | 晋升时真正写入规则库 | v0.3 提出 2 条（其中 1 条经审查不合格，见 5.1） |

**"每轮替换而非累加"是一个重要设计**：如果提示词补丁每轮都堆上去，跑十轮后提示词会长到模型读不完，且无法判断是哪一轮的补丁在起作用。这也是 v0.4 一次性加 7 条导致问题的原因之一。

### 5.3 版本管理与可追溯性

- 版本号从 `versions/` 目录扫描最大值递增，避免"连续两轮都生成 v0.2 互相覆盖"（此 bug 已修复并有测试覆盖）；
- 每个版本记录 `change_log`，字段包括：`time` / `from` / `to` / `proposal` / `proposal_source` / `diagnosis` / `changes` / `evidence` / `status`；
- `evidence` 里保存当轮的纠错案例统计与混淆对，可以回答"这条改动是基于哪几条纠错";
- 晋升与回退命令：`promote --version v0.3` / `rollback --version v0.2`。

v0.4 的 `proposal_source` 字段如实记录了 `rule_based_fallback（模型提案失败，已回退）`——这类信息如果被美化掉，后续就无法解释为什么第二轮的改动风格与第一轮差别那么大。

### 5.4 两轮进化的实际效果

见第 4.2 节第三行与 4.5 节的分析：**未带来提升**。机制本身可用（提案、晋升、回退、追溯全部跑通），问题出在提案质量与叠加策略上——而这恰恰是人工确认环节应该拦下来的地方。本次实验中 `auto_evolve` 为了跑通三组对比采用了自动晋升，跳过了人工审查，这是一个流程上的简化，**不应作为实际使用方式**。

## 第 6 章 失败案例与局限性

### 6.1 工程缺陷（已修复）

**E7：图片格式不兼容导致 41.9% 的样本静默失败**

第一次用真实模型跑 43 个测试样本时，基础组有 **18 个样本（41.9%）** 的 `model_calls = 0`、`findings` 为空，但 `duration_ms` 有 700~1200 ms。三组的 Macro F1 全是 0.000。

原因有两层：

- **数据层**：Pexels 的 CDN 会按请求头里的 `Accept` 返回 **AVIF** 格式，而文件仍以 `.jpg` 落地。本地看图正常（Pillow 按内容识别），但模型接口直接返回 `400 code 1210 图片输入格式/解析错误`。
- **代码层**：`agents.py` 的 `except Exception` 把调用失败转成 `{"findings": []}`，于是「模型没跑成」和「画面确实没有风险」在报告里**长得一模一样**。

危害在于：这批失败样本会被当成"未发现风险"计入统计——若真相是有风险，漏报被静默吞掉；若真相是正常，则是白捡的准确率。**这类 bug 比模型判错更危险，因为它伪装成"系统很保守"。**

修复：统一转真 JPEG 并从请求源头去掉 `image/avif`；`AgentTrace` 增加 `error` 字段、`AnalysisReport` 增加 `analysis_errors`；评测把失败样本**单列并排除出 P/R**，对比表新增"分析失败"列。修复后同批样本零失败。

**教训：「无输出」和「无风险」必须在数据结构上分开。**

（另有 E1~E6 六个工程缺陷记录在 `docs/失败案例记录.md`，包括"模拟结果被标成 confirmed""对照组恒为 0 分""视频瞬时误检被当确认"等。）

### 6.2 模型判断失败案例（真实、未修正）

以下五条均来自本次测试集的真实输出，未做美化。

**M1：最自信的判断恰恰是错的（误报）**

| 项 | 内容 |
| --- | --- |
| 输入 | `synth_confuse_10`：实验室地面完全干燥，只有一道斜向窗光在亮面瓷砖上形成反光带，砖缝与浮尘清晰可辨 |
| 系统输出 | `spill_or_obstruction`，**置信度 1.00**，复核 Agent 判定 confirmed |
| 正确答案 | `normal` |
| 原因 | 感知 Agent 把高光带读成"积水"，复核 Agent 说"证据明确具体"从而放行。**两个 Agent 一起错，且高度自信** |
| 是否修正 | 未修正。这条正是 v0.4 想通过"易混淆说明"解决的，但 v0.4 整体过度保守，效果被抵消 |

这条最能说明"证据复核"的边界：复核 Agent 检验的是"证据是否支持结论"，**它不检验证据本身的真假**。当两个 Agent 基于同一个错误观察时，复核反而会把错误确认得更牢。

**M2：缺失型风险被系统性忽略（漏报，4/4）**

| 项 | 内容 |
| --- | --- |
| 输入 | `synth_ppe_missing_02`：两名学生在通风橱前操作，均穿便装、未戴护目镜，一人手持烧杯 |
| 系统输出 | `flammable_near_heat`（"实验台上有一个加热装置和一个装有红色液体的烧瓶，两者距离较近"），置信度 0.8 |
| 正确答案 | `ppe_missing` |
| 原因 | 模型只注意画面里**显眼的物体**（加热装置、烧瓶），完全没去看人是否戴护目镜 |
| 是否修正 | 未修正。4 个 `ppe_missing` 测试样本全部未识别，该类召回为 0 |

**根因：这是「缺失型风险」，与「存在型风险」是两类不同难度的问题。** `spill_or_obstruction`、`food_or_drink` 是存在型——画面里有显眼物体，看到就能报。`ppe_missing` 是缺失型——要判断"应该戴护目镜但没戴"，模型必须①锁定人脸 ②判断眼部有没有透明护目镜 ③结合"正在做液体操作"推断应该戴。全景图里人脸只有几十像素，透明护目镜几乎不留视觉特征，模型直接跳过这一步。

这个失败模式对改法有直接指导：`ppe_missing` 不能靠"再强调一遍要检查护目镜"，**必须先用 `crop_region` 把人脸裁出来放大再判断**——这正是 Agent 自主工具调用本该发挥作用的地方，但当前模型没有主动申请。**这是下一版最明确的改进点。**

**M3：试剂桶被当成饮料杯（漏报 + 误报同时发生）**

| 项 | 内容 |
| --- | --- |
| 输入 | `synth_reagent_management_05`：台面边缘一个大塑料溶剂桶敞口缺盖，旁边小烧杯也敞口无标签 |
| 系统输出 | `food_or_drink`（"在实验台上可以看到一个装有液体的玻璃杯，这表明可能有食物或饮料出现在工作区域内"），置信度 0.8 |
| 正确答案 | `reagent_management` |
| 原因 | 把"敞口容器装液体"这一视觉模式匹配到了"饮料杯"上，完全忽略容器形态（溶剂桶 vs 杯子）与标签缺失这一核心证据 |
| 是否修正 | 未修正 |

**M4：通道堵塞完全没看到（漏报）**

| 项 | 内容 |
| --- | --- |
| 输入 | `synth_spill_or_obstruction_05`：实验台之间通道被推车、凳子、仪器箱堵死，安全出口几乎不可见 |
| 系统输出 | 无任何风险 |
| 正确答案 | `spill_or_obstruction` |
| 原因 | 画面里没有"异常物体"——推车、凳子、箱子都是实验室常见陈设，模型没有"通行空间被占"这一空间推理能力 |
| 是否修正 | 未修正 |

这与 M2 同源：**都需要"判断本该有什么而没有"，而不是"判断有什么"**。

**M5：保温杯证据不足被放弃（漏报）**

| 项 | 内容 |
| --- | --- |
| 输入 | `synth_food_or_drink_03`：不锈钢保温杯放在仪器和笔记本旁 |
| 系统输出 | 无任何风险 |
| 正确答案 | `food_or_drink` |
| 原因 | 保温杯外观接近普通器皿，模型未能确认其为饮用容器。严格说弃权（判 `uncertain`）比沉默更合理，但系统直接无输出 |
| 是否修正 | 未修正 |

**一个共性**：五条里有四条（M2/M4/M5 及部分 M3）都指向同一个问题——**模型对"观察不到"没有自觉**。它不会说"我看不清这个人的眼部"，而是转而报告一个看得见的别的东西，或者干脆沉默。这是当前多模态模型在安全审查类任务上的通病，也是本系统最需要改进的地方。

### 6.3 系统局限

1. **数据集一半是合成图**。合成图的光照、构图、噪点分布与真实手机照片不同，模型可能在合成图上表现更好。**换成实拍后必须重跑全部实验，不能沿用本次数字。** 这是本项目最大的外部效度限制。
2. **类别严重不均衡**（normal 占 61%）。未做重采样，Macro 指标本身也有波动——`ppe_missing` 只有 4 个测试样本，一个样本的翻转让召回在 0 和 0.25 之间跳。
3. **依赖模型自身能力**，换模型版本会导致结果漂移，本次结果只对 `glm-4v-flash` 成立。
4. **规则库覆盖有限**，未收录的情形一律输出 `uncertain`，这是设计选择而非缺陷。
5. **视频是决策层融合，未做目标级跟踪**。无法回答"同一个危险物在画面里如何移动"，也无法处理遮挡后重现。
6. **单帧图像无法判断动态风险**（如"人员正在靠近热源"），这类风险需要视频与目标跟踪。
7. **缺失型风险是硬伤**（见 M2/M4），当前召回为 0。
8. **复核 Agent 不检验证据真假**（见 M1），两个 Agent 同时误读时会互相确认。

### 6.4 后续改进计划

按收益从高到低：

1. **强制人脸裁剪**：对 `ppe_missing`，在感知阶段无条件调用 `crop_region` 裁出人脸区域放大后再判断。这是针对 M2 的直接修复，预期能把该类召回从 0 提到可用水平。
2. **引入空间推理**：针对 M4，用目标检测框计算通道可用宽度，把"空间被占"变成可量化的证据。
3. **增加"观察不到"的显式出口**：允许 Agent 输出"该区域被遮挡/分辨率不足，无法判断"，而不是被迫沉默或转而报别的风险。这是针对 M1/M5 的共同解。
4. **自进化改为少量多次**：每轮只改 1~2 条，改后立即在 dev 上复测，避免一次堆 7 条无法归因。
5. **扩充真实数据**：组员实拍 30~50 张真实违规场景，替换部分合成样本后重跑。
6. **接入目标检测**：`detect_objects` 已实现接口，安装 ultralytics 并训练小模型后可启用。

## 附录 C：数据与代码的诚实性声明

1. 测试集中 **49 张为文生图合成样本**，非真实拍摄。本项目在数据集、实验、报告中均逐处标注，未将合成数据表述为实拍。
